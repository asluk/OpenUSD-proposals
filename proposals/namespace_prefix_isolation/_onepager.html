Namespace & Prefix Isolation for USD Extensions

AOUSD TAC discussion input — 2026-09-04 — Aaron Luk (NVIDIA)

Draft, under active review — not complete, not an AOUSD position, not citable. Originally prepared for the 2026-09-04 TAC meeting, now being revised based on that discussion. Derived from the working README; content is still changing.

Problem

  • USD's extension surface is an open set (properties, schema/type names, metadata keys, file formats, resolvers, and more not yet named) — don't scope requirements to today's list.
  • Concrete failure mode: two vendors independently name an extension identically with different semantics → silent data corruption when assets move between tools.

Terminology & hierarchy composition

Prefix = leading ownership token(s). Namespace = the space it scopes. An identifier carries two independent axes: owner hierarchy (who governs — a flat vendor token, or a multi-level hierarchy the owner defines for itself) and domain hierarchy (what functional area, how specific a feature).

AOUSD.GeomWG . brep  →  owner = alliance > WG (AOUSD has no sub-WGs today, but the convention must support that depth if added later); domain = schema-level token shared by BrepArray + its API schemas (UsdSolid B-rep proposal, PR #109, Aaron Luk & Joe Umhoefer)
yoyodyne.tierA . dimensional.contabulator  →  a single vendor's own internal sub-hierarchy — not necessarily "working groups"
yoyodyne . dimensional.contabulator  →  flat, no sub-hierarchy

Functional Requirements

Properties a solution must satisfy — not a syntax. Delimiter/casing/notation are solution-space choices, left open.

  • Namespace & Prefix Isolation (own requirement, split from Discoverability):
    • R1 Ownership legibility
    • R2 Hierarchical scoping (both axes)
    • R3 Owner sub-hierarchy independence — applies to a single vendor too, not just consortiums
    • R4 Syntax may vary by extension surface — no single notation mandated
    • R5 Collision-prevention guarantee
    • R6 Tiered/graduated lifecycle — sequential, but starting point can vary (needn't start at vendor level)
    • R7 Proportionate governance cost
  • Discoverability (separate): extension points · unified extension model · discovery/registration (per Gordon Bradley) — Profiles' ProfileAPI is a candidate vehicle, not mandated

Open Questions for TAC

  • Which collision-prevention strength: registry, convention, or resolve-time detection? (R7 governance-cost tradeoff)
  • Does coverage extend beyond properties to schema/type names, file formats, resolvers?
  • Can namespace/prefix isolation ship independent of discoverability?
  • TAC front-line + SC escalation, or dedicated WG?

Design Considerations

Separability from OpenUSD's plugin system. The namespace/prefix paradigm and its enforcement must be definable and usable independent of pluginfo.json, C++ namespace macros, dlopen loading, or any other runtime mechanism. Even inside ProfileAPI, the query contract (what explicit/introspective queries return) is implementation-agnostic — only the registration mechanism (pluginfo.json) is OpenUSD-plugin-specific. AOUSD should govern the former, not mandate the latter.

Profiles as the cross-cutting declaration mechanism: namespace/prefix isolation is the naming layer; it doesn't address how an asset declares which extensions it requires. ProfileAPI's query contract is an existing, already-accepted mechanism for that — one candidate vehicle for Discoverability, not a mandated one. Governance of how vendor extensions fold into profiles is deferred to AOUSD, consistent with how Profiles itself defers canonical-capability governance to OpenUSD/AOUSD.
